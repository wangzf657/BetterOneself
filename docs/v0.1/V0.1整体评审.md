# V0.1 整体评审

> 日期：2026-11-20｜评审基线：commit `4532e59`
> 范围：`product/` 四份文档、`technical/` 四份文档，以及《决策记录》《注意事项》
> 性质：开发前静态设计评审；不表示代码、真实样书或真实模型链路已经验证

## 1. 结论

**评审结论：有条件通过。当前不建议按现文档直接进入全量核心开发，但可以立即启动工程骨架、格式解析 spike 和契约测试夹具。**

产品方向、范围收缩和总体技术路线成立，22 条需求也都有页面或接口映射。当前阻塞不在于“功能没设计够”，而在于少数底层契约互相矛盾或缺少可执行规则：

- 哪些节点能学习、点亮并进入进度分母；
- AI 拆分、合并怎样确定性迁移原文引用；
- 规划、恢复、重解析怎样保护已有学习证据；
- 简答题怎样计分，3/4/5 题分别怎样通过；
- 用户作答和逐题判分结果怎样持久化并回看。

上述问题会直接影响表结构、状态机、API 和验收。若在实现中由各开发者自行补规则，容易造成返工、进度失真或学习数据丢失。

### 开发准入判断

| 工作 | 当前是否可开始 | 条件 |
|---|---|---|
| 前后端工程骨架、OpenAPI 生成、测试框架 | 可以 | 不提前固化有争议的业务规则 |
| PDF / EPUB / TXT / Markdown 解析与引用定位 spike | 可以 | 仍按【待验证】记录，不提前宣称格式验收完成 |

| 各模块完整开发 | 有条件开始 | 对应 P1 在模块开工前关闭；P2 不阻塞 |

**不需要为此扩大 V0.1 范围。** 推荐用“限制危险操作 + 明确简单口径”解决，不引入通用学习数据迁移、消息队列、账号体系或后续候选功能。

## 2. 评审分级

- **P0**：阻塞核心开发；可能造成数据丢失、点亮不可信，或实现者无法得到同一结果。
- **P1**：对应模块开发前必须澄清；主要造成异常路径缺失、跨文档矛盾或安全/一致性风险。
- **P2**：可在开发中处理；主要是文案、呈现和可复现性优化。

本次归纳 **5 项 P0、13 项 P1、8 项 P2**。相同根因的问题合并处理，避免把同一缺陷重复计数。

## 3. 做得合理、应保留的设计

1. **范围收缩正确。** 只验证“导入 → 骨架 → 学 → 测 → 点亮”，后续候选没有混入本版验收（`product/需求分析.md:54-73`）。
2. **结构先于 AI。** 目录识别零 LLM，原树先可见，规划失败保树，直接回应了前身入口慢、贵、碎的问题（`product/需求列表.md:27-30`）。
3. **导入不预生成讲解和题目。** 成本随学习量而非藏书量增长，阶段 A/B/C 的解耦方向合理（`technical/技术方案.md:54-70`）。
4. **知识点与检索切片分离。** 会话、笔记、测验、点亮都挂知识点，chunk 只承担检索和引用（`technical/数据模型.md:7-12`）。
5. **点亮语义诚实。** 一次通过即点亮、永久保留，不冒充长期记忆；点亮由 service 判定而不是相信 LLM 输出（`technical/数据模型.md:196-202`）。
6. **三框会话围绕核心学习动作。** 原文、陪学、笔记职责清楚，引用回跳、折叠和窄屏降级均有明确反例。
7. **星盘与工作树职责分离。** 星盘负责进度仪式与导航，工作树负责整理，没有让游戏化承担全部操作。
8. **技术复杂度克制。** 不引入 LangGraph、Celery、通用 skill 平台和重排器；SQLite + BackgroundTasks 足以支撑单机 V0.1，前提是补齐恢复与幂等规则。
9. **验证纪律正确。** LLM 自动化全部 mock，真实样书人工抽评和真机冒烟单列，PDF 等待验证项没有伪装成已完成（`technical/技术方案.md:246-269`）。

## 4. P0：核心开发前必须关闭

### P0-01　学习单位、可点亮节点与统计分母不统一

**证据**

- 产品要求“任意节点可直接开始学习”（`product/需求列表.md:32`）。
- 章内路径只排列叶节点，父节点作为路段名（`product/页面清单.md:165-167`）；原型却又给有子节点的“4.2”展示学习中状态和学习入口（`product/原型设计.md:188-197`）。
- 创建会话只要求 refs 非空（`technical/接口设计.md:125-127`），进度却只统计叶子（`technical/数据模型.md:180-194`）。
- 当前“叶子 = 无未排除子节点”，排除全部子节点后，原父节点可能突然进入分母。

**问题与影响**

父节点、章节点、部分层是否能独立学习和点亮没有唯一答案。父节点可能“测验通过但不计进度”，也可能与子节点重复统计；排除子节点还可能让分母意外变化。书架、星盘、工作树和 API 会得出不同结果。

**最小修正**

- 推荐最薄规则：**只有结构上无子节点、未被排除且 refs≥1 的学习单元可进入正式学习、测验和点亮；父节点与部分层只是容器，只显示聚合进度。**
- “结构叶”按是否有子节点判断，不能因子节点被排除而变成叶节点。无子节点的章可以是学习单元。
- 将“任意节点开放”改为“任意有效学习单元开放，无顺序解锁门槛”。
- 若产品坚持父节点也能独立学习，则需反向取消叶子限制，并另行解决父子重复统计与星盘入口；两种方案可选其一，不能维持现状。

**验收补例**

父子均有 refs 时父节点不能独立点亮；排除全部子节点不会改变父节点的容器属性；章无子节点时可学习；树、会话和书架使用同一分母。

### P0-02　AI `split/merge` 不是可执行的数据契约

**证据**

- 规划输入只有节点、篇幅、页跨度和可选摘要，输出包含拆分与合并（`technical/技术方案.md:102-114`）。
- 校验只规定节点 ID、同章、相邻和数量，没有新节点字段、层级限制和 refs 分配规则（`technical/技术方案.md:134-143`）。
- 学习依赖 `knowledge_refs`，数据模型却假设拆分后会自然挂引用（`technical/数据模型.md:108-110,191`）。

**问题与影响**

例如把含 20 个 chunks 的节点拆成 3 个节点，规划器既看不到 chunk 清单，也没有输出边界 chunk ID，service 无法知道每个新节点应获得哪些原文。合并也没有规定同级/叶节点限制、refs 去重和旧节点处置。结果可能无来源、漏挂、重挂或不可重放。

**最小修正**

- 为五类操作补 Pydantic schema 和应用不变量。
- `split` 输入增加有序 ref manifest：`chunk_id`、顺序、标题路径、定位、`char_count`，不需要增加正文；输出用边界 chunk ID 表示区间。
- 拆分区必须是对原 refs 的**完整、有序、互不重叠分区**；合并仅限同章、同父、相邻结构叶，refs 按原顺序取去重并集。
- 明确旧节点保留、转容器或删除的规则；操作和 refs 迁移在同一事务完成，无法分配则整项失败保树。

**验收补例**

20 chunks 拆成 3 段后总数、顺序和内容完全一致；重叠、遗漏、跨父、跨级、含学习证据的操作全部拒绝且不留半次结果。

### P0-03　规划、恢复与重解析的学习证据保护不闭合

**证据**

- 规划冲突只比较表示用户编辑的 `updated_at`，手动 replan 不限制已有学习数据（`technical/技术方案.md:118-123`、`technical/接口设计.md:92-94`）。
- planning 中只要 refs 就绪就能创建会话（`technical/接口设计.md:125-127`）。
- 恢复原目录只用“会话消息数为 0”代表无学习证据（`technical/数据模型.md:204-212`）；但用户可不生成讲解，直接写笔记或测验并通过。
- 初始快照未包含完整稳定 ID、章锚点和 refs 映射，产品却要求恢复不影响手动编辑（`technical/数据模型.md:124-132`、`product/页面清单.md:191-198`）。
- 重解析删除旧 chunks 并保留会话、测验，历史消息和答案仍持有旧 chunk 引用（`technical/数据模型.md:148,160,218`）。

**问题与影响**

存在多条破坏证据的路径：学习后 replan 再拆分/合并；零消息但有笔记、quiz 或点亮时恢复原目录；重解析后历史引用 404。即使记录仍在，也可能挂到错误学习单元或无法回跳，违背“证据不丢”和“点亮永久保留”。

**最小修正**

V0.1 不做通用学习数据迁移，采用统一窄规则：

1. 学习证据包括任一 `session / message / quiz / note / lighted_at`，不能只看消息。
2. 自动规划应用时，在写事务内重新检查目标及后代；有证据或用户编辑冲突则跳过该项并记事件。已有证据后，手动 replan、恢复原目录和破坏性重解析返回 409。
3. 恢复原目录还需排除 planning 中的 stale 写入；快照保存稳定节点 ID、层级、章锚点及 refs 对应关系。不能可靠保留手动编辑时，应明确拒绝或明确列入将撤销内容，不能静默覆盖。
4. 失败重试与无目录重识别可以保留；解析先写暂存数据，完整成功后一次替换。若确需支持有证据重解析，则必须保留 source/chunk 版本，而不是删除旧引用。
5. `last_kp_id`、历史消息、quiz refs 和笔记都纳入同一不变量。

**验收补例**

planning 中学习、学习后 replan、零消息但有 quiz、零消息但有笔记、恢复时已有手动编辑、重解析后打开历史错题；均不得丢数据或产生静默进度变化。

### P0-04　简答题计分与固定通过线未定义

**证据**

- 测验以客观题为主但允许简答题，简答题只要求具体评语（`product/需求列表.md:48`）。
- 通过线只有“4 题对 3”的示例，要求不可静默调整（`product/需求列表.md:49-50`、`product/需求分析.md:161-168`）。
- API 对简答题也返回 `correct`，并计入同一个 `correct_count`，但没有正误规则或 rubric（`technical/接口设计.md:180-196`）。

**问题与影响**

实现者无法判断简答题是否等权计分、由谁判正误，也无法确定 3 题和 5 题的通过数。若由模型临时给通过线或宽松判分，同一学习方法可能产生不同点亮标准，破坏“通过线不可绕过”。

**最小修正**

- **推荐最薄方案：正式点亮测验只让客观题计分；简答练习不计入点亮成绩。** 若坚持简答题计分，必须定义结构化 rubric、二元 `correct`、评语和判分失败路径。
- 每道计分题二元且等权；通过线由 service 使用固定映射，例如 3 题对 2、4 题对 3、5 题对 4，所有学习方法与历次测验一致。
- 将“客观题即时判定”明确为“整组提交后由代码立即判定”，避免与提交前不泄露答案冲突。

**验收补例**

3/4/5 题临界分、含简答题、判分失败、三种学习方法、同节点多次重考；通过线都不能被模型或 UI 改变。

### P0-05　测验表没有保存用户作答与逐题判分结果

**证据**

- `quizzes` 只有题面、标准答案/解析、通过线、总正确数和是否通过（`technical/数据模型.md:153-166`）。
- 提交响应和历史回看却都包含 `per_question`、用户正误和简答评语（`technical/接口设计.md:180-200`）。
- 产品要求历次测验与错题评语可回看（`product/需求列表.md:51`）。

**问题与影响**

用户选了什么、简答写了什么、逐题正误和本次生成评语没有持久化位置。刷新后无法复原提交结果，B4-04 和点亮证据下钻无法按文档实现。

**最小修正**

不新增表，至少在 `quizzes` 增加：

- `submitted_answers_json`：用户实际作答；
- `grading_results_json`：逐题正误、评语、扣分点和返回用 refs。

标准答案/解析仍只存服务端；提交后一次性写入作答、判分、总分和 passed。点亮依据可通过该节点首次 passed quiz 查询，或显式保存 `lighted_by_quiz_id`，与“最近一次测验”分开。

**验收补例**

刷新和重进后逐题内容、用户答案、评语完全一致；点亮后重考失败，仍能回到首次通过证据，且原点亮时间和状态不变。

## 7. 推荐的克制优化

1. **不做学习证据通用迁移。** V0.1 用“有证据后禁止破坏性结构操作”替代复杂的拆分继承、合并继承和历史结构版本系统。
2. **正式测验先固定简单计分。** 客观题二元等权 + 固定通过线最容易复验；简答若保留为练习，不参与点亮。
3. **不新增测验历史表。** 在现有 `quizzes` 增加作答与判分 JSON 即可满足回看。
4. **不升级异步基础设施。** 保留 BackgroundTasks，用数据库状态认领、启动恢复和幂等键解决崩溃与双击，不引入 Celery。
5. **不让 embedding 成为核心链路单点。** 当前节点 refs 足以支撑基础讲解和出题，向量只补跨节点细节。
6. **砍掉没有验收价值的附加按钮。** 归档、单题变式、全局删除等不影响最薄闭环验证，优先少做而不是补更多接口。
7. **不提前做虚拟化和拖拽布局。** 先用真实样书测量树规模与会话性能，再决定是否需要优化。

## 9. 最终判断

**V0.1 值得进入开发，但应“分阶段准入”，不应把当前文档直接冻结为全量施工契约。**

最稳妥的路径是：现在启动基础工程与格式 spike，同时用一次集中文档修订关闭 5 项 P0；随后按模块关闭 P1，即可进入完整开发。P2 和真实模型质量优化不应阻塞开工，但真实样书与真机冒烟未通过前，不得宣称对应格式或 V0.1 验收完成。
