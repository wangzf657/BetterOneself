## 1. 技术选型

原则:**只选领域头部、社区活跃、许可证宽松的框架;能复用不自研**。

| 层 | 选型 | 理由 | 备选(何时切换) |
|---|---|---|---|
| 后端语言 | Python 3.12+ | LLM/RAG 生态最厚;团队=自己 | — |
| Web 框架 | FastAPI + Uvicorn | Python API 框架事实标准,Pydantic 类型驱动,自带 OpenAPI 文档 | — |
| 数据校验 | Pydantic v2 | FastAPI 原生集成 | — |
| ORM/数据库 | SQLAlchemy 2.x + SQLite | 单机单用户零运维(WAL 模式);备份=拷文件 | V2.0 多用户时换 PostgreSQL |
| 向量检索 | sqlite-vec + 硅基流动 BAAI/bge-m3 | 与 SQLite 同库零进程;bge-m3 中英双语均优;硅基流动免费档实测可用(2026-11-18,1024 维) | 免费档限流影响导入时换付费档或本地模型 |
| LLM 接入 | openai SDK(OpenAI 兼容协议);默认 GLM Coding Plan | 实测可用(2026-11-18):专用端点 `open.bigmodel.cn/api/coding/paas/v4`(勿用通用 v4,会绕开套餐路由),默认模型 glm-5.3-flash;Anthropic 端点亦通,但只接一种协议 | 换 provider 只改 .env;多路由再评估 LiteLLM |
| Agent 编排 | LangGraph 1.x | 有状态多步流程(拆解流水线、学习会话状态机)的头部框架;可持久化检查点 | — |
| LLM 工具链 | 仅 langchain-core + langgraph | 只用文档抽象与编排,不引全家桶 | — |
| 间隔重复 | py-fsrs(`pip install fsrs`) | FSRS 官方 Python 实现(Anki 同源算法),不自研排程 | — |
| PDF 解析 | Docling | IBM/MIT 维护;表格/代码块结构保留好,自带 OCR(扫描版可用);RAG 导向 | 中文扫描件多再评估 MinerU |
| 网页正文 | trafilatura | 网页正文提取头部库,去噪效果好 | — |
| GitHub 导入 | httpx 直调 GitHub REST API | 只用 3-4 个端点(树/内容/README),不值得引 PyGithub | 需求变复杂再换 |
| 前端框架 | React 19 + Vite + TypeScript(strict) | 用户指定;头部组合 | — |
| UI 组件 | shadcn/ui + Tailwind CSS 4 | 用户指定(2026-11-18 确认);代码归自己,可定制 | — |
| 服务端状态 | TanStack Query | 请求缓存/重试事实标准 | — |
| 图可视化 | @xyflow/react(原 ReactFlow) | 依赖图/知识树可视化的头部库(M2-02) | — |
| E2E 测试 | Playwright | 跨浏览器头部 E2E | — |
| 后端 Lint | ruff(lint+format)+ mypy(宽松) | 一件套搞定,速度快 | — |
| 前端 Lint | ESLint + Prettier + tsc strict | 标准件 | — |
| 部署 | Docker Compose(前端静态构建,后端挂 SQLite 卷) | 单部署一键起;开发模式裸跑 | — |

**依赖图可视化以外的 UI 复杂件**(知识点树、分日计划列表、卡片流)当前无头部 React 库可直接抄:知识点树/计划用常规组件自建,规模(几十~几百节点)不需要虚拟化。

**LLM 实测约束(2026-11-18,GLM Coding Plan,key 经 .env 注入不入库)**:

1. 套餐**不含 embedding**(v4 embeddings 返回 1113 余额不足)——embedding 独立走硅基流动 BAAI/bge-m3(OpenAI 兼容,免费档,批量嵌入需分批+重试,见 2.5)
2. 本产品属官方分类的"通用 Agent 工具"档位:**尽力交付策略,高负载时可能动态排队/限流**——自用验证阶段可接受,V2.0 商业化前须切正式 API 计费
3. glm-5.3-flash 为思考型模型:短问答也会产生 reasoning tokens,max_tokens 别给太小;正式参数按场景在 agents/ 内调

## 2. 架构设计

### 2.1 系统结构

```
┌───────────────────────────────────────────────┐
│  frontend/  React SPA(shadcn/ui)              │
│  features: study·sources·knowledge·plan·      │
│            learn·review·mastery·settings      │
└──────────────┬────────────────────────────────┘
               │ REST(JSON) + SSE(对话流式)
┌──────────────┴────────────────────────────────┐
│  backend/app                                  │
│  api/        FastAPI 路由,薄层,只做参数校验    │
│  services/   领域服务(四环+档案),业务核心      │
│  agents/     LangGraph 编排(见 2.3)           │
│  ingest/     资料导入适配器(docling/           │
│              trafilatura/github)               │
│  models/     SQLAlchemy 表                     │
└──────────────┬────────────────────────────────┘
               │ SQLAlchemy 2.x
        SQLite(业务数据 + sqlite-vec 向量)
```

### 2.2 领域模块与产品概念的映射

services/ 按产品概念模型(总纲第 6 节)划分,一个概念一个模块,闭环在代码结构上可见:

| 模块 | 覆盖概念 | 主要职责(对应需求) |
|---|---|---|
| studies | Study | 项目 CRUD(M1-01) |
| sources | Source | 资料管理、重解析(M1-05),调用 ingest/ |
| knowledge | KnowledgePoint | 知识点树/依赖图 CRUD 与编辑同步(M2-01/02/03) |
| planning | Plan / Task | 计划生成装配、确认、手动调整、逾期重排(M2-05/06, M5-02) |
| learning | Session | 会话编排状态、测验判定、卡片沉淀触发(M3-*) |
| review | Card / 复习队列 | py-fsrs 排程、四档评分、薄弱点标记(M4-*) |
| mastery | MasteryProfile | 掌握状态机+证据链(M6-*) |
| nudges | Nudge | 今日任务聚合、每日摘要、周复盘、回炉(M5-*) |

跨模块数据流:**知识点是枢纽**——所有模块外键指向 knowledge point,与总纲概念模型一致。

### 2.3 LLM 编排边界(防止过度编排)

LLM 调用分两类,**不是所有 AI 功能都上 LangGraph**:

- **LangGraph(有状态多步)**:
  - 拆解流水线:资料 chunk → 知识点抽取 → 依赖推断 → 计划草案。图结构、重试、结构化输出校验由框架管
  - 学习会话:讲解/苏格拉底引导/测验评分的状态机,检查点持久化到 SQLite,支持会话中断恢复
- **直接 openai SDK(单次调用)**:卡片生成、简答评分、摘要文案等一问一答场景。包一个 `llm()` 薄函数统一重试与结构化输出

### 2.4 异步与调度(刻意从简)

- **导入解析**:API 立即返回 source 记录(状态=processing),解析跑在 FastAPI BackgroundTasks;状态落库,前端轮询。重启丢任务 → 状态停留在 processing,提供"重新解析"入口兜底。**不上 Celery/消息队列**(单机自用,运维成本>收益)
- **每日逻辑(逾期重排/每日摘要/周复盘)**:惰性触发——首次打开首页时检测并执行,结果落库。V1.0 督促本来就发生在"打开产品时",与产品形态一致。V1.1 IM 推送时再引入常驻调度

### 2.5 RAG 与引用

- chunk 粒度:按解析后的 Markdown 标题+段落切分,每 chunk 记录 source_id + 结构化定位(章节/页码/行),这是"引用可点击回跳"(M2-01, M3-02)的数据基础
- embedding:硅基流动 BAAI/bge-m3(OpenAI 兼容端点,1024 维;免费档有限速,导入时批量嵌入分批+失败重试);检索 = sqlite-vec 余弦相似 + 结构过滤(限定 study/source)
- 讲解回答的引用由 LLM 标注 chunk_id,前端渲染为可点击引用

### 2.6 安全与数据边界

- API Key 加密落库(cryptography Fernet,密钥存本机文件,不入库),任何日志与 LLM 请求上下文不得包含明文 key(M7-01)
- 无账号体系,API 默认只监听本机/内网;Docker 部署时由用户自行决定暴露范围
- 全量导出(M7-03):按表导 JSON + 学习报告导 Markdown,与产品原则"开放而非锁定"对应

## 4. 代码规范

总原则(ponytail 精神,全项目有效):**最小完整改动;不写没人要的抽象/配置/兜底;删除优于新增;注释只写代码说不出的"为什么"**。

### 4.1 Python(backend)

- ruff:`E,F,I,UP,B,SIM` 规则集,format 用 ruff 内建;line-length 100
- mypy:默认宽松,models/services 公共函数要求类型注解
- 命名:模块/函数 snake_case,类 PascalCase;service 函数动词开头(`generate_plan` / `reschedule_overdue`)
- Pydantic schema 是 API 唯一出入参形态;service 层不出现 dict 满天飞
- SQLAlchemy:禁止在 service 层裸拼 SQL;查询收敛在各 service 内,不跨模块互查表(通过对方 service 的函数)

### 4.2 TypeScript/React(frontend)

- tsc strict;ESLint(recommended + react-hooks)+ Prettier
- 组件:函数组件 + hooks;features/ 内按"页面/组件/hooks/api"分文件,不搞深层嵌套
- 服务端状态一律 TanStack Query(useQuery/useMutation),不手写 loading 状态;本地 UI 状态用 useState/context,不为小状态引库
- API 类型从后端 OpenAPI schema 生成(openapi-typescript),禁止手写重复类型
- 样式只写 Tailwind 原子类;超过一屏的样式逻辑抽组件,不写自定义 CSS 文件

### 4.3 通用

- 注释:解释"为什么"与非显约束;不复述代码;设计动机归 docs/,不进代码注释
- shortcut 标记:明知受限的简化写 `shortcut: <限制>, <何时升级>` 注释,形成技术债台账
- 死代码:自己改动产生的孤儿必清理;既有死代码只提醒不动手
- Commit:Conventional Commits(`feat: ...` / `fix: ...` / `docs: ...`),一个 commit 一件事

## 5. 开发流程

### 5.1 前置(一次性)

```bash
git init && git add -A && git commit -m "docs: 产品总纲与技术总纲"
```

分支:单人开发,main + feature 分支;每个需求/修复一条分支,自测通过合回 main。

### 5.2 功能开发闭环(每个需求都走)

```
1. 定位需求:从 v1.0/需求.md 找到 ID 与验收标准(它是完成的唯一定义)
2. 防重复造轮子:GitHub/官方文档检索同类实现(原则:闭环比新写优先)
   → 有可借鉴:记下 repo 与借鉴点;没有:自己设计,复杂处写 3-5 行设计说明
3. 测试先行:核心逻辑先写失败测试(见第 6 节分层)
4. 实现:最小改动,遵守第 4 节规范
5. 验证:新测试 + 全量回归绿;对照验收标准逐条勾
6. 提交:Conventional Commits,需求 ID 进消息(`feat: M4-02 四档评分`)
```

### 5.3 里程碑(与需求第 6 节验收路线一致)

1. 能学(导入→拆解→讲解)→ 2. 能考(测验→卡片→队列)→ 3. 能规划(计划→今日任务→重排)→ 4. 能督促(薄弱点联动)→ 5. 补全(网页/repo 导入+P1/P2)

每个里程碑收尾跑一遍 E2E 主链路(见 6.3),它是"闭环未断"的机器证明。

### 5.4 设计评审点(何时必须停下来先写文字)

以下改动**先写 3-10 行设计说明进 docs/(或 issue),再动手**:

- 新增外部依赖 / 换掉表内选型
- 数据模型改动(models/ 加表改列)——SQLite 迁移成本高,想清楚再写
- LangGraph 图结构变更(agents/)
- 任何"我觉得以后会用到"的功能冲动——写下来,通常会发现不需要

## 6. 测试要求

务实分层:**核心逻辑高覆盖,LLM 边界契约化,UI 靠 E2E 主链路**。不追全项目覆盖率数字。

| 层 | 工具 | 必测范围 | 要求 |
|---|---|---|---|
| 后端单元 | pytest | 计划生成/重排算法、FSRS 集成与队列上限、掌握状态机与证据链、薄弱点判定、Key 加密 | 覆盖核心分支;目标:services/ 行覆盖 ≥80% |
| 后端集成 | pytest + httpx(TestClient)+ 内存 SQLite | 每个里程碑的 API 关键路径(上传→解析→拆解) | 里程碑收尾前全绿 |
| Agent 契约 | pytest + LLM mock | LangGraph 图结构、提示词装配、结构化输出 schema 校验、苏格拉底模式分支 | 不测 LLM 输出质量(人工抽评),只测管线正确 |
| 前端组件 | 不强制 | — | 纯展示组件不写测试;有复杂交互(四档评分流)再补 |
| E2E | Playwright | **一条主链路**:建项目→导入 MD→拆解→确认计划→完成学习任务→答题错一题→次日复习该卡→重排可见 | 每个里程碑收尾必跑绿;这是"闭环没断"的唯一定义 |

LLM 相关测试一律 mock(`responses`/自写 stub),CI 与本地不花真实 token;真实 LLM 效果用开发期的手动冒烟脚本(`backend/scripts/smoke_*.py`)抽验。

## 7. 环境与命令

```bash
# backend(uv)
cd backend && uv sync && uv run uvicorn app.main:app --reload

# frontend(pnpm)
cd frontend && pnpm install && pnpm dev

# 质量
cd backend && uv run pytest && uv run ruff check . && uv run mypy app
```
