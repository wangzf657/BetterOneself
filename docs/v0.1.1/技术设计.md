# V0.1.1 技术设计：导入管线与 AI 规划

> 日期：2026-11-23｜状态：已实现（2026-11-24 全链路测试通过，见[实现进度.md](实现进度.md)）
> 基线：[V0.1 技术方案](../v0.1/technical/技术方案.md)（§4 导入、§6 skills、§8 检索、§9 流程）；本文档只写**增量与变更**，未提及部分沿用 V0.1。

## 1. 新管线时序

取代 V0.1 技术方案 §4/§9 的「三阶段 + 自动拟大纲」时序：

```
上传对话框（B6-01 勾选「使用 AI 规划」，默认不勾）
  ↓
解析（零 LLM，不变）：提结构 → 硬切片落库（MAX_CHARS 上限不变）→ 星图页原树可学
  ↓
统一预检（新）：embedding 必检；LLM 仅勾选时检
  ├─ embedding 通 → embedding 后台任务立即启动（不等任何确认）
  ├─ 不通 → 分路提示（B6-02），星图页重试入口（B6-06）
  ↓
[勾选且 LLM 通] 确认页（新）：消耗预估 + 计划天数/学习目标输入 → 用户「开始规划」
  ↓
AI 规划（原「拟大纲」，触发方式变更）：章摘要 → 全局规划 → 建议**暂存不应用**
  ↓
树确认页（新）：五类操作逐条勾选（含学习证据/编辑复查）→ 应用 → 引用重挂 → 完成
```

关键时序原则：

- **切片与 embedding 先行**：切片由标题层级决定、向量只算切片文本，两者与树结构无关（V0.1 的三层解耦不变），规划的确认闸门只挡「AI 结构生效」，不挡读原文、不挡 embedding。
- **规划拆成两段**：生成（LLM 调用）与应用（写库）之间插入用户确认，建议暂存于新表（§5）。
- **确认前原树可学** → 应用时树上可能已有学习证据，V0.1 `apply_operations` 的逐条复查（edited 快照对比、`subtree_has_evidence`、逐条 skip）**全部保留**，新增行为仅是「复查结果从后台静默跳过变为确认页预标注」（B6-04 验收 2）。

## 2. 状态机增量

### Source.embed_status 增 `precheck_failed`

```
pending → precheck_failed（预检不通，含维度不一致）→ [手动重试，先重预检] → pending → running → ready / degraded / failed
```

- 预检不通不再启动任务，`embed_error` 写明分路原因。
- `precheck_failed` 只能由用户手动重试离开（B6-06），不自动重试。

### Study.outline_status 增 `precheck_ok`、`precheck_failed`、`awaiting_confirm`

```
未勾选：idle → structure_ready（驻留；原树可学，规划路不显示）
勾选：  idle → structure_ready → precheck_ok（预检通，等用户点「开始规划」）
                             ↘ precheck_failed（手动重试先重预检，通过则回 precheck_ok）
        precheck_ok → planning → awaiting_confirm（建议已生成，等树确认）→ ready
                                   ↘ skipped（用户「全部拒绝」）
        planning 崩溃 → failed（生成失败，保树，语义同 V0.1）
```

- 未勾选时 `outline_status` 停在 `structure_ready`，不再走 V0.1 的 `skipped`；是否启用由 `Study.use_ai_planning`（§5）判定，它就是 B6-05「未启用」的依据。
- `precheck_ok` 与 `awaiting_confirm` 均为**可恢复的等待态**：用户关闭确认页或页面后状态保留，星图页入口可续（B6-03 验收 5、B6-04 验收 4）。`skipped` 只表示「用户全部拒绝了建议」。
- 启动恢复（`recover_on_startup`）变更：删除 V0.1「`structure_ready` 且无 `planning_started` 事件则自动排规划任务」——规划只能由用户经 `planning/start` 启动；`awaiting_confirm` 无后台任务、无需恢复；`planning` 崩溃后按 V0.1 语义转 `failed`，**已暂存的建议保留**，重试时可直接回到 `awaiting_confirm`（不重花 token 重新生成）。

## 3. 预检实现口径

| 路 | 方法 | 通过条件 | 不通归类 |
|---|---|---|---|
| embedding | 对固定短文本（如「预检」）发一次真实 embedding 请求 | 请求成功**且**返回维度 = 1024（`vec_chunks` 建表固定 `float[1024]`，非空库时即等于已有向量维度） | 未配置 / 请求失败 / 维度不一致 |
| LLM | 一次最小 chat 请求（max_tokens=1） | 请求成功返回 | 未配置 / 请求失败 |

- 维度基准：`vec_chunks` 的建表语句固定 `float[1024]`，没有「空库记基准」的存储位，判定就是「维度 == 1024」；不一致时原因写明「期望 1024，实际 N」。
- 维度一致性校验是硬门槛：V0.1 真机调试踩过「换 embedding 模型后维度不符写脏 vec 表」的坑，预检是拦截这一静默脏数据的唯一前置点。它拦不住「同为 1024 维的不同模型混入」，记入后续候选，不在 V0.1.1。
- 预检请求用独立的短超时（15 秒、不重试），不复用正式调用的 180 秒超时——否则不通的服务会把一次预检挂到三分钟。
- 预检结果落 `Source.embed_error` / `Study.outline_error`（`precheck_failed` 态），前端据状态与原因分路提示（B6-02 验收 3 的四组合）。
- 预检本身每次各一条最小请求，成本忽略不计；LLM 预检仅在勾选路径发生。

## 4. 消耗预估口径

确认页（B6-03）展示的两路预估，全部由已落库数据静态计算，**不调用任何 API**：

- **embedding 消耗**：`E = Σ chunk.char_count × k_cn`，中文系数 `k_cn ≈ 1.2` token/字，展示为「约 X token」（取整到千）。
- **AI 规划 token 区间**（输入为主、输出小）：
  - 摘要输入 `Σ_ch min(章字数, 12000) × k_cn`（12000 为 V0.1 `CHAPTER_SUMMARY_CHAR_CAP`）；
  - 摘要输出 `章数 × 300`（每章摘要估 300 token）；
  - 规划输入 = 树 JSON + refs 清单 + 摘要汇总，按落库数据实测字数 × `k_cn`；
  - 规划输出 ≈ 2000；
  - 区间取 `[合计 × 0.9, 合计 × 1.3]`，展示为「预计 A–B token」。
- 估算函数纯静态、可单测（输入章数/字数分布，输出区间），不依赖 mock LLM。

## 5. 数据模型增量

沿用 V0.1「先写设计再迁移」，均为**只增不改**：

```
Study 增三列：
  use_ai_planning  BOOLEAN  NOT NULL DEFAULT 0     -- B6-01，上传勾选；B6-05「未启用」的判定依据
  planned_days     INTEGER  NOT NULL DEFAULT 10    -- B6-03，1–365，仅档案与规划上下文
  learning_goal    TEXT     NOT NULL DEFAULT '学透这本书：合上书也能讲清楚'  -- ≤200 字

新表 planning_proposals（建议暂存，确认应用的唯一来源）：
  id          INTEGER PK
  study_id    INTEGER FK→studies
  thesis      TEXT            -- 全书总述（随确认写入 Study.outline_thesis）
  ops_json    TEXT            -- 全部五类操作（含每条 AI 理由与复查标注）+ snapshot（生成时各节点的 updated_at）
  status      TEXT            -- pending / applied / declined / superseded
  created_at / applied_at
```

- `use_ai_planning` 必须落库：崩溃重启后 `run_parse` 会重排，勾选不能只活在请求里。
- `snapshot` 与建议同存（V0.1 它只是进程内变量）：确认可能发生在生成后很久，应用时仍以「生成那一刻」的 `updated_at` 判定「生成后被编辑过」。
- 同一 study 允许多条历史记录（declined 后重规划），仅一条 `pending`，用部分唯一索引 `WHERE status = 'pending'` 约束；应用时该条转 `applied`，旧 pending 转 `superseded`。「恢复原目录」「重解析」会把 pending 建议置 `superseded`——树已变，建议作废。
- 章节摘要仍按 V0.1 落在 `KnowledgePoint.chapter_summary`，应用操作时随节点迁移/合并（merge 后两份摘要拼接截断，split 后子节点继承原摘要），迁移规则作为 V0.1.1 的单测点。
- 迁移：新增 Alembic `0002`，列与表已存在则跳过——`0001` 用 `create_all`（建的是**当前**模型），全新库走 `0001` 时已带上新结构，不能再加一次。

## 6. 接口增量

在 [V0.1 接口设计](../v0.1/technical/接口设计.md) 基础上新增（命名遵循现有风格）：

| 方法与路径 | 用途 | 对应需求 |
|---|---|---|
| `POST /studies/{id}/precheck` | 触发统一预检。体 `{lanes?: ["embedding", "llm"]}`（缺省两路）；同步执行，返回两路结果与不通原因。解析完成后由后台线程调用，手动重试复用同一逻辑 | B6-02、B6-06 |
| `GET /studies/{id}/estimate` | 消耗预估（§4，静态计算）：`{embedding_tokens, planning_tokens: [下限, 上限]}` | B6-03 |
| `POST /studies/{id}/planning/start` | 体 `{planned_days: 1–365, learning_goal: ≤200 字}`，存入 Study 并确认启动（`precheck_ok → planning`）。条件更新原子认领，重复点击第二次返回 409 | B6-03 |
| `GET /studies/{id}/planning/proposal` | 取当前 pending 建议（含逐条复查预标注） | B6-04 |
| `POST /studies/{id}/planning/proposal/apply` | 体 `{proposal_id, selected: [操作下标]}`，应用所选 + 引用重挂（`awaiting_confirm → ready`） | B6-04 |
| `POST /studies/{id}/planning/proposal/decline` | 体 `{proposal_id}`，全部拒绝，保树（`awaiting_confirm → skipped`） | B6-04 |
| `GET /sources/{id}/original` | 原文文件（见 §8.4） | B6-07 |
| `GET /sources/{id}/assets/{path}` | 从原始文件按需读 EPUB 资源（见 §8.3）：图片等二进制直接返回，XHTML 返回 sanitize 后的 HTML 片段 | B6-07 |

既有端点改动：`POST /studies` 表单增 `use_ai_planning: bool`（B6-01）；`GET /studies/{id}/progress` 响应中 `outline` 块增加 `stage`（章摘要 x/y 等，供 B6-05 章级进度）与 `ai_planning`（B6-05「未启用」判定）；节点内容响应增加 `source_id` / `source_type`（原文视图取文件用）；`reembed` 改为「先预检、通过才启动」，允许从 `precheck_failed / failed / degraded` 发起；`reparse` 的学习证据 gate 不变。**移除** `POST /studies/{study_id}/outline/replan`——其职责由 `precheck`（LLM 路）+ `planning/start` 承担。

## 8. 学习页原文双视图与图片资源（B6-07）

### 8.1 视图与定位桥

| 格式 | 原文渲染 | 定位锚点（来自 chunk.location） |
|---|---|---|
| EPUB | sanitize 后的 XHTML（图片经资产端点显示） | href + 标题锚点 → 打开该文件、滚到标题锚点 → 再按切片首段文本匹配细化到段落 |
| PDF | pdf.js 整页渲染 | 页码区间 → 跳起始页 |
| TXT | 纯文本 | 行区间 → 滚动定位 |
| MD | 渲染（外链图可见；本地相对路径图占位提示） | 行区间 |

location 坐标系 V0.1 已有，双视图只是它的第二个消费方；前端在两种视图间互相同步定位，toggle 状态按学习项目记忆。

EPUB 的 location 只有 `{href, anchor?}`、没有段落区间（同一节的切片共用一个锚点），所以段落级定位靠文本匹配，**不改解析层**——已有的书直接受益。反向切换（原文 → 解析文本）同理：PDF/TXT 按当前页码/行号反查切片，EPUB/MD 按可见文本片段匹配切片，匹配不到则回到上次定位的切片。

### 8.2 图片处理口径（决策 #41）

**图片走原文视图，不进文本管线**：chunk 内容、char_count、消耗预估（§4）、向量输入全部保持纯文本，图片对 tutor/quiz 文本链路无意义。

- EPUB：不预提取、不落新存储——原始 zip 常驻 uploads（`Source.stored_path`），资产端点按需读取；
- PDF：不提取图片（pypdf 提图成本高、图注对齐难），原文视图整页渲染即含图；
- MD：单文件导入下本地相对路径图片本就不可达，明确占位提示；外链图片原文视图直接加载，加载失败显示占位不报错；
- 解析文本视图内嵌图片占位（「此处有图 → 点击查看」）**不在 V0.1.1**：图-chunk 对齐是新的解析复杂度，原文视图已兜底，是否值得做待真机观察切换频率（后续候选·学习增强）。

### 8.3 资产端点安全（EPUB 属外部输入）

- 路径：只允许 zip 内规范化相对路径，拒绝 `../`、绝对路径、盘符（含编码后的 `%2e%2e`、反斜杠、空段、NUL）；校验后按名字**精确匹配** zip 条目，不用它拼文件系统路径；匹配不到返回 404 而非 500；
- XHTML：后端用 `nh3` 白名单消毒后返回——剥离 script/style/`on*` 事件属性，丢弃外链图片与 `a@href`，保留 `id` 供锚点定位；`img@src` 相对路径重写为资产端点 URL；
- 图片 Content-Type 白名单：png/jpeg/gif/webp；svg 用 lxml 剥离 script/`on*`/`javascript:` 后以 `image/svg+xml` 返回；白名单外类型拒绝（415）；
- 缓存：资源不可变（对应原文件版本），响应带长缓存头 + `X-Content-Type-Options: nosniff`。

### 8.4 原文文件端点（`GET /sources/{id}/original`）

双视图需要 PDF/TXT/MD 的原文件，V0.1 没有对应端点：

- PDF：原字节，`application/pdf`，支持 Range 请求（pdf.js 分段读取）；
- TXT / MD：`text/plain` / `text/markdown`，下发**规范化后**的文本（与切片同源，否则行号对不上 `location.line_start`）；
- 原文件缺失或读取失败时，前端在原文视图内报错，解析文本视图不受影响（B6-07 验收 5）。

## 9. 测试策略（沿用 V0.1 分层纪律）

- 单测：预估函数（§4）、状态机流转（§2 含两等待态与崩溃恢复）、预检判定（未配置 / 请求失败 / 维度不一致三种原因；短超时）、摘要迁移规则（§5）、迁移 `0002`（带数据的 `0001` 旧库升级后旧数据在、新列新表在；全新库升级不报错）。
- LLM 一律 mock：预检、规划生成不花真 token；「维度不一致拒启动」必须有显式用例（真机教训的回归锚点）。
- E2E：勾选→预检→确认→树逐条确认→可学的完整链；不勾选→纯本地路径→可学；确认前在原树学习→含证据条目被预标注取消；关闭确认页→星图页续办；双视图切换双向定位、EPUB 原文含图渲染、资产端点路径穿越被拒。
- 资产端点专项：路径穿越（`../`、编码斜杠、绝对路径、盘符）、XSS（含 script 的 XHTML 被 sanitize）、svg 剥离、Content-Type 白名单外类型拒绝、条目缺失 404 而非 500——均为显式安全用例。
- 回归：V0.1 全量用例适配新时序后保持绿；被 B6-04 取代的「自动应用」用例改写而非删除（对应 V0.1 需求修订，留痕）。
