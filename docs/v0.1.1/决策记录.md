# V0.1.1 决策记录

> 编号接续 [V0.1 决策记录](../v0.1/决策记录.md)（#01–#33）。日期：2026-11-23｜状态：待评审。

## #34 AI 规划改为 opt-in + 双确认（取代自动应用）

- **决策**：上传时勾选「使用 AI 规划」（默认不勾）；token 消耗确认 + 规划结果逐条确认两道闸门，确认前不生效。
- **动因**：树是产品的信任锚，先奏后斩优于先斩后奏；BYO-Key 下大额消耗须知情。V0.1 的「自动应用 + 事后恢复」依赖用户事后发现与手动悔改。
- **已否决**：维持自动应用、仅加强事后回滚提示——信任损伤发生在「树被改了而我不知道」的瞬间，事后提示无法弥补。
- **影响**：B2-03 信任策略修订（见[需求变更](需求变更.md)）；`apply_operations` 复查逻辑保留但前移到确认页预标注。
- **评审修订（2026-11-23）**：树确认页「直接关闭」= 保留建议、不记事件、不重花 token，状态停在 `awaiting_confirm` 可续办；只有「全部拒绝」才记 `planning_declined` 并转 `skipped`。（原文「直接关闭也记 declined」与「等待态可恢复」互斥。）

## #35 管线时序重排：切片与 embedding 先行、引用确认后重挂

- **决策**：切片落库与 embedding 不等规划确认；规划应用时按最终树重挂 `knowledge_refs`（行级迁移，向量与切片零重算）。
- **动因**：切片由标题层级决定、向量只算切片文本，与树结构天然解耦（V0.1 已实现的三层解耦）；切片先行同时保住原文可读、split 的 chunk 区间坐标系、embedding 早可用。
- **已否决**：「先定树再切片再 embedding」的整体后置方案——确认闸门会阻塞读原文与检索，且 split 失去 chunk 坐标系；纯 V0.1 现状——AI 自动改树不可接受（#34）。

## #36 预检统一置于解析完成之后，重试必先重预检

- **决策**：embedding 必检（含返回维度一致性），LLM 仅勾选时检；预检不通过不启动对应任务；手动重试入口先重预检再启动。
- **动因**：上传时章数字数未知，预估无从谈起；解析是零 LLM 秒级环节，等它完成再预检成本可忽略。维度校验拦截「换 embedding 模型写脏 vec 表」的静默故障（V0.1 真机调试教训）。
- **已否决**：上传对话框内预检——文件未解析，预估误差可达数倍；预检失败静默转任务 failed——重蹈「失败静默」覆辙。

## #37 embedding 不设确认、AI 规划 token 需确认

- **决策**：embedding 预检通过即后台启动，消耗仅提示；AI 规划需用户在确认页点「开始规划」。
- **动因**：embedding 单价低一两个数量级、一本书成本几分钱且必跑，为它加确认是过度交互；规划 token 分钟级且为可选功能，必须知情。
- **已否决**：两路都确认——用户点击次数无谓翻倍。

## #38 「AI 拟大纲」改名「AI 规划」，仅对外文案

- **决策**：UI 文案、API 语义描述、文档统一「AI 规划」；代码标识符（`outline_planner`、`outline_status`、`OutlineEvent` 等）不改名。
- **动因**：「拟大纲」偏排版动作，「规划」更贴「AI 参与决定学什么、怎么分组」的实际行为；代码改名会无差别波及 V0.1 全部用例与事件历史数据，收益为零。

## #39 确认页新增计划天数与学习目标，只作上下文与档案

- **决策**：确认页输入计划学完天数（默认 10，1–365）与学习目标（默认「学透这本书：合上书也能讲清楚」，≤200 字），存 Study 并进入规划 prompt。
- **动因**：用户节奏与目标影响规划的排除/合并激进度与总述口吻，且是后续 tutor 因果链的输入；两字段成本低、价值随版本递增。
- **边界（防蠕变）**：不生成学习计划、不做排期、不做督促——均属[后续候选·计划与督促](../v0.1/后续候选/)。
- **已否决**：默认目标用「学透这本书」裸文案——不带检验口径，无法与「读完就行」区分；默认文案与需求分析「看讲解觉得懂，合上书讲不出来」的痛点对齐。

## #40 AI 规划进度可见到章一级

- **决策**：规划状态在「章摘要」阶段展示第 x/y 章，`pipeline_progress` 增 `stage` 字段。
- **动因**：真机每批 ~65s、全书分钟级，无进度变化的等待必然被用户判读为卡死（V0.1 真机教训：慢≠卡，但用户无从分辨）。
- **已否决**：笼统 spinner + 规划中百分比——批内无子进度可算，百分比只能是假进度。

## #41 原文双视图；图片走原文视图、不进文本管线

- **决策**：学习页原文面板增加「解析文本 / 原文」切换，默认解析文本，按 chunk.location 双向同步定位；图片只在原文视图呈现（EPUB 从原始 zip 按需 serve、PDF 整页渲染、MD 仅外链），chunk 内容/char_count/预估/向量保持纯文本。
- **动因**：解析是有损工作表示（丢图、丢排版、可能出错），原文是无损参照，需要兜底入口；location 坐标系 V0.1 已有，双视图零解析层改动。图片对检索与 tutor/quiz 文本链路无意义，进 chunk 只会污染字数与预估口径。
- **已否决**：图片提取进 chunk 或解析文本内嵌图片占位——图-chunk 对齐是新的解析复杂度，收益待真机验证（放后续候选·学习增强）；PDF 提取嵌入图片——成本高、图注对齐难，整页渲染已含图；上传时预提取图片资产目录——原 zip 常驻 uploads，按需读取零新增存储。
- **评审修订（2026-11-23）**：① V0.1 的 EPUB location 只有文件路径与标题锚点、没有段落区间，定位口径改为「打开文件 → 滚到标题锚点 → 按切片首段文本匹配细化」，不改解析层；② 引入成熟依赖而非自写：`pdfjs-dist`（PDF 渲染）、`react-markdown` + `remark-gfm`（MD 渲染）、`nh3`（XHTML 白名单消毒）；③ 新增 `GET /sources/{id}/original`，PDF/TXT/MD 的原文件此前没有端点。
